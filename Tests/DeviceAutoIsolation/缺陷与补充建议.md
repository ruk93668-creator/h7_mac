# 自动注册、自动初始化：缺陷与补充建议

范围：当前 CM4 Device_RegisterAll、Device_InitAll 和 Framework_InitRuntime。
结果：15项仿真，14项符合预期，1项安全检查失败。仅新增隔离测试，未修改生产源码。

## 已验证正常

- 真正使用 DEVICE_EXPORT 产生 Flash 导出表，并通过 Image$$ER_DEVICE_EXPORT$$Base/Limit 遍历。
- Framework 先在 BUS 等级注册，再在 DEVICE 等级初始化；auto_init=false 的设备也注册，但不初始化。
- NULL导出项、重复导出、无效名称及非法首次注册状态正确返回错误，并停止后续初始化等级。
- 自动设备缺少init回调返回 NOT_SUPPORTED；回调失败保留原错误码、设备进入ERROR。
- 已注册链表的头尾、节点数量及 next/prev 双向关系通过检查。

## 确认问题：初始化回调可重入自身

复现步骤：

1. 导出设备a和c，两者auto_init=true。
2. a的init回调首次执行时调用Device_Init(a)，测试仅允许一次递归以避免栈溢出。
3. 调用Framework_InitRuntime。

预期：拒绝正在初始化的对象重入，a和c各执行一次init。
实际：嵌套Device_Init(a)返回SYS_OK，回调顺序为a→a→c；整体启动仍返回SYS_OK。

原因：Device_Init在调用生命周期回调前，设备仍处于UNINIT；只有回调返回后才更新为READY/ERROR。嵌套调用因此再次通过状态检查。
若实际回调无条件递归初始化自身，可能造成无限递归和栈溢出。

建议：在进入回调前建立“初始化进行中”标志或明确的INITING状态；重入返回BUSY/INVALID_STATE，退出时清理标志。也需考虑间接循环依赖a.init→b.init→a.init。
本次未实现该保护。

## 需要明确的策略

| 事项 | 当前实测行为 | 补充建议 |
|---|---|---|
| 重复自动注册 | 第二次RegisterAll返回ALREADY_EXISTS；链表未损坏 | 明确只允许启动时调用一次，或明确设计幂等策略；不要盲目忽略所有重名错误 |
| 重复/提前初始化 | InitAll遇到已经READY的auto_init设备返回INVALID_STATE，后面的设备不会初始化 | 若希望可重试，明确是否跳过READY；ERROR设备的恢复应独立设计 |
| 失败回滚 | 已注册对象和已READY设备保留，后续等级停止 | 当前行为符合Fail-fast；应记录失败设备及操作，不能假设错误返回意味着全量撤销 |
| 初始化期间注册设备 | a.init注册extra后，同轮InitAll继续初始化extra | 明确冻结注册阶段、拒绝初始化期间注册，或接受动态遍历并规定数量和依赖约束 |
| 未注册先InitAll | 空Registry返回SYS_OK | 如果接口仅由Initcall调用，阶段顺序已有保障；若允许外部直接调用，可增加阶段检查 |
| 同级设备依赖 | 自动初始化沿导出/注册顺序遍历，没有显式优先级 | 依赖关系不能仅依靠源码或链接顺序；可要求init独立，或另行设计依赖/优先级机制 |

## 启动调用方的静态风险

当前CM4 main在Framework_InitRuntime失败后，仅进入含注释的空故障处理分支，随后仍进入Framework_Run循环。
这是源码静态检查结果，本次没有执行带真实HAL的main。

建议：明确初始化失败后的安全停机、降级或恢复策略，避免上层继续假定所有auto_init设备已READY。
