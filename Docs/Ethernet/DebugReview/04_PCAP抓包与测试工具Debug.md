# PCAP 抓包与测试工具 Debug

## C05 在线通过而磁盘 PCAP 缺数据

### 1. 问题背景

PC 在 Npcap 回调获得包后，需要在线校验及离线复放两种独立证据。

### 2. 第一次异常

旧 E3.5 文件有记录头和 caplen，但读盘无法恢复各包的 payload。

### 3. 最初的怀疑

首先区分 snaplen 截断、Npcap 丢弃和应用序列化错误。

### 4. 排查过程

git show 309447b 证实旧 e35_peer.py 将 packet 读入内存、写记录头后直接在线检查；修复只增加 capture.write(packet)。

### 5. 关键突破

只有 16 B 记录头而没有对应包体，下一条记录头会被解析器当作上一包 payload。

### 6. 根因及修复

**CONFIRMED**。写盘遗漏包体已确认。保留旧文件；在线 JSON 的依据仍是内存检查。

### 7. 验证结果

修后 6 秒探针离线核对板端 599、PC 383 帧。371 原始 PCAP 本轮用 tshark 读取 124075 条，历史复放 62000/61999 匹配、619.558 s。[E3_5_VALIDATION](../E3_5_VALIDATION.md)

### 8. 底层原理

全局头与每包记录头只描述时间、捕获长度及线上长度。caplen=frame.len 是单包长度声明，仍须核对记录真正存在。

### 9. 最终经验

每次测试都做一次从磁盘读取到 EOF 的抽查，不能只读脚本成功行。

### 10. 面试复盘

E3.5 的在线统计通过后，我发现磁盘 PCAP 无法用来复放。我查了 Npcap 到文件的边界，发现脚本已经拿到完整 packet 并用它核验序号，但往磁盘只写每包记录头，遗漏 payload。我在历史补丁里确认改动只是加一次 capture.write(packet)。修后用短探针独立重放，再用 371 会话验证十分钟级双向流量。旧 JSON 仍能支持在线校验的结论，旧抓包没有包体就不能补造。这个案例展示了怎样发现测试证据本身的缺陷，而不误判驱动。


## C06 VLAN 长度与会话串扰

### 1. 问题背景

验收从 60、512、1514 B 到有 VLAN 的边界。必须约定是否包含 FCS。

### 2. 第一次异常

复用 VLAN 会话 354 后统计混入；1518 B 与 1522 B 的描述容易被当成不同负载。

### 3. 最初的怀疑

可能是测试序号重复、网卡/驱动剥标签、FCS 口径不一致或真实包长错误。

### 4. 排查过程

用新会话 355、期望 VID 7、筛选双向帧，再对账起止窗口。

### 5. 关键突破

软件读到 1518 B、线上加 4 B FCS 为 1522 B，两者可对应同一帧。

### 6. 根因及修复

**CONFIRMED**。已确认 354 有会话污染并排除出正式对账；355 在线结果恢复。

### 7. 验证结果

355 双向 1000/1000 和 1499/1499；旧版 PCAP 降级。1514 重测仍缺同会话驱动增量。[E3_5_VALIDATION](../E3_5_VALIDATION.md)

### 8. 底层原理

未加 VLAN 最大软件帧 1514 B，加四字节 tag 为 1518 B。抓包端若剥 tag，应以实际配置和字段为证。

### 9. 最终经验

记录网卡、BPF、会话 ID、caplen、len、FCS 口径及双向交集。

### 10. 面试复盘

测试最大帧时同时遇到两个口径问题。第一，带 VLAN 的软件帧是 1518 字节，线上把 FCS 算进去是 1522；第二，复用旧会话编号会使相同序号混入统计。我们弃用污染后的 354，用新会话 355 过滤 VID、方向和序号，并记录板端收齐 1000 与 PC 收齐 1499。旧版 PCAP 有包体缺陷，因此这一轮的结论限定为在线验证。面试时我会从一个具体帧开始数头部、tag、载荷和 FCS，并说明如何把计数绑定到一次试验。

PC 选 “以太网 3” 等实际有线口，先确认 link、源 MAC 和板端目的，再发送。PC 注入返回或抓到本机 TX 只能证明本机发送路径；需要板端交付和序号才确认接收。已复读 `output/Ethernet/rx_*.pcapng` 的若干 60 B 样本，这些早期文件与 E3.5 有缺载荷的旧 `.pcap` 是不同工件。
