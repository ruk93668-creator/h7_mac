## R1.1 普通任务取得终结结果

Flipper Storage 把请求完成同步对象随命令传递，Storage 处理结束后由服务解除同步对象。V3 保留请求与完成之间的关联，采用固定、按值的结果槽，并通过零等待 API 取回。 [Storage API](https://github.com/flipperdevices/flipperzero-firmware/blob/a8a24de3ff394f77d599ea8ba9c073398670c880/applications/services/storage/storage_external_api.c) · [Storage 消息完成](https://github.com/flipperdevices/flipperzero-firmware/blob/a8a24de3ff394f77d599ea8ba9c073398670c880/applications/services/storage/storage_processing.c)

1. IPC、Camera、USB、Storage 中的普通调用任务，使用目标 Service 的 `*_Request(command_id, operation, argument)`。内部识别实际任务身份；结果槽先绑定 `请求任务 + Service + command_id`，命令随后尝试入队。请求未入队时撤销该预留，可用原编号重试。返回 `SYS_OK` 表示命令已入队。
2. 每个普通任务全局最多持有一项待终结或未取走的结果。槽还在使用时，新提交返回 `SYS_ERR_BUSY`。这样 Control 无需因结果接收方滞后再次阻塞，也不会覆盖旧结果。Control 作为请求方仍使用原同步订阅和多项连续提交。
3. Service 仍按原 ACK/FAULT 和背压规则向 `APP_CHANNEL_CONTROL` 交付。Control 实际取出消息并验证后，先将匹配结果按值写入对应任务的槽，再发 `RUNTIME_EVENT_WAKE` 通知并执行原同步观察者。错误身份或无预留的终结消息进入协议拒绝诊断。状态只在短 FreeRTOS 任务临界区内更新；通知与回调均在临界区之外执行。
4. 提交者以自身上下文调用 `AppV3Business_TakeResult(service, command_id, &result)`。返回 `SYS_ERR_BUSY` 表示该命令仍在推进；`SYS_ERR_NOT_FOUND` 表示没有匹配项或已经取过；`SYS_OK` 表示取走终结记录，`result.result` 才是业务 ACK/FAULT 的实际结果。通知丢失或合并时，调用者仍可在其事件循环中轮询。结果保留至实际取走，业务侧超时不回收或覆盖结果。

Control 同步 PubSub 不向其他任务开放订阅。正在执行的回调自行撤销其票据会得到 `SYS_ERR_BUSY`，其他任务撤销返回 `SYS_ERR_INVALID_STATE`。回调退出后，Control 可以完成撤销并释放 Context。同步回调仍可撤销本轮尚未执行的其他订阅，新订阅从下一条事件起生效。

## R1.2 历史消息通道

`APP_CHANNEL_CAMERA_COMMAND`、`APP_CHANNEL_USB_COMMAND`、`APP_CHANNEL_TO_CAMERA`、`APP_CHANNEL_TO_USB` 的常量、编号和固定槽保留。发送在入队和通知前返回 `SYS_ERR_NOT_SUPPORTED`；接收固定返回 `false`。这一行为不依赖调用任务，避免通过原角色伪装成已交付。原业务结果 `APP_CHANNEL_CONTROL` 与启动 `APP_CHANNEL_STARTUP` 继续正常收发；未启用图像帧交接。
