# V3.2A-A3 — USB UVC 旧提交退场证据与最小整改申请

基线 `be43ddeda895887bd6dfdcfe399ec30737ba74b2`，分支 `codex/application-v3-media-usb`。状态 **BLOCKED，等待退场接口与 STOP 顺序审批**。本轮只提交源码审计与实施方案。

## 1. 现有接口的证据边界

| 事实 | 冻结源码 | 对 A3 的影响 |
| --- | --- | --- |
| Submit 成功只表示 Payload 接受源帧 | [USB_UVC_SubmitFrame / SubmitFrameView](../../../CM7/Service/usb_uvc_class.c#L256) 在现有 USB IRQ 锁内核对 CONFIGURED、Commit、Alt 1、端点和 WAIT_FRAME，成功后进入 WAIT_SLOT | 原函数没有返回帧级提交凭据。App 应由唯一 UsbTask 调用者关联一次成功 Submit，返回 BUSY 或 ERROR 的帧未被 Class 接受 |
| 正常末包有可信提交点 | [UVC_DataIn](../../../CM7/Service/usb_uvc_class.c#L1063) 核对端点与 IN 完成序号，[USB_UVC_Process](../../../CM7/Service/usb_uvc_class.c#L406) 核对包 token 并推进 Payload，末包完成才递增计数。[Payload_FinishFrame](../../../CM7/Service/usb_uvc_payload.c#L319) 清除两个源 span | 包 token、完成计数和 Class 指针无法单独关联旧 Application 租约。只有当前有效 Class 的状态查询能读取 frame_owned |
| 取消登记和读者退出是两件事 | [USB_UVC_CancelFrame](../../../CM7/Service/usb_uvc_class.c#L315) 只设 CANCELLING。[USB_UVC_Process](../../../CM7/Service/usb_uvc_class.c#L381) 对在途包先要求 [Platform Abort](../../../CM7/Platform/usb_device.c#L488) 成功，失败保留恢复状态和 Payload | 由原 Cancel/Process 推进。是否已归还要看对应提交的最终退出事实 |
| Alt0、Reset、Disconnect、取消配置可能让 Class 消失 | [UVC_SetStreamAlt](../../../CM7/Service/usb_uvc_class.c#L1003) 先封提交并关闭 EP1，成功后处理 Payload。[UVC_DeInit](../../../CM7/Service/usb_uvc_class.c#L512) 成功后清除 s_uvc_active。[USB_UVC_GetStreamStatus](../../../CM7/Service/usb_uvc_class.c#L335) 遇到空 Class 返回 INVALID_STATE | s_uvc_payload 是 Class 外静态对象。旧 Class 消失后现有公开 API 无法核对该次 Submit 的源引用清理事实。新 Class 复用固定池地址也不能替代证明 |
| 端点退出与源引用清理可能不是同一个结果 | [UVC_ReleaseFrame](../../../CM7/Service/usb_uvc_class.c#L1105) 不检查 AbortPacket 返回值，并继续清包和设置 WAIT_FRAME。[Usb_Reset](../../../CM7/Platform/usb_device.c#L1387) 与 [Usb_Disconnect](../../../CM7/Platform/usb_device.c#L1456) 在 Class 清理失败后仍继续关闭遗留端点 | 即使 EP1 最后关闭，仍须核对旧 Payload 的两个源引用、pending token 以及同次提交。BUSY、超时、INVALID_STATE、新 Class 的空闲状态都不能授权 RETURN |
| 当前 STOP 顺序会挡住 A3 读者退出 | [UsbService_StopDevice](../../../CM7/ApplicationV3/Services/USB/usb_service.c#L352) 在 s_frame 非 IDLE 时先返回 BUSY，排在 CheckFrame/Cancel 前。[UsbService_ObserveDevice](../../../CM7/ApplicationV3/Services/USB/usb_service.c#L430) 把任何 frame_owned 当成异常 | 若直接加 Submit，正常在传帧也可能进 FAULT。STOP 将等待运输退休，而运输在 A3 必须先等 UVC 退出，需要在同一 UsbTask 内把旧帧推进放在整设备 STOP 门禁之前 |

当前源码未发现 `USB_UVC_SubmitFrame` 在 CM7 的生产调用者。A3 接入后应维持 UsbTask 为唯一提交者，其他组件不应写入此读者凭据。冻结代码使用 Packet 构建复制源 span，BSP 当前关闭 USB 内部 DMA；软件仍须等待 Class 对源帧和在途包的完整退出。Camera DCMI 的七槽约束照旧。

## 2. 申请批准的最小只读接口

候选只新增一个公开查询。保留 `USB_UVC_SubmitFrame()`、`USB_UVC_GetStreamStatus()`、Cancel 和 Process 的签名及应用消息 ABI。

```c
typedef enum
{
    USB_UVC_READER_EXIT_NONE = 0,
    USB_UVC_READER_EXIT_EOF,
    USB_UVC_READER_EXIT_CANCELLED,
    USB_UVC_READER_EXIT_CLOSED
} UsbUvcReaderExit_t;

typedef struct
{
    uint32_t accepted_id;
    uint32_t retired_id;
    UsbUvcReaderExit_t retired_reason;
    SysResult_t accepted_first_fault;
} UsbUvcReaderProof_t;

SysResult_t USB_UVC_ReadReaderProof(UsbUvcReaderProof_t *proof);
```

- **唯一写入权威。** UVC Class 在现有 USB IRQ 锁保护下维护一个固定证据记录，放在可随 DeInit 释放的 Class Context 之外。任务 API 与原 IRQ 回调使用同一保护域。IRQ 只执行常量次数的赋值，无队列、分配或等待。查询由 UsbTask 正常上下文调用，参数和上下文检查通过后即使 Class 已解绑也能一致读取。候选预计包含 4 个定长字段，实际 ARMCC5 布局与 RAM 待构建。
- **提交与关联。** 零为无凭据。只有 `PayloadStartView` 成功才在提交所在临界区分配非零 accepted_id，并开始本次首错记录。先检查编号耗尽，拒绝回绕。唯一 UsbTask 可在 Submit 前后读取 accepted_id 来绑定这次 A2 request/generation/lease；USB IRQ 只提交退休事实，不分配新 accepted_id。IRQ 若在 Submit 返回到查询之间成功关闭旧 Class，证据仍保留。若读回不符，隔离原租约并保留错误，不再次 Submit。
- **退休写入点。** EOF 只在匹配末包确认并清完两段源引用后记录；取消仅在无在途硬件读取且 Payload 成功停止，或平台 Abort 成功且匹配 pending token 被实际解除后记录；Alt0、DeInit 仅在真实端点 Close 成功且 Payload 确认源引用及包已清后记录。原 `UVC_ReleaseFrame` 改为可检查的内部结果，失败时 `UVC_SetStreamAlt` / `UVC_DeInit` 保留原未确认状态，禁止借 WAIT_FRAME 或 Class 解绑伪造成功。已退休的 ID 和原因不因无帧 Close、重复回调或后来的成功被改写。
- **有界保留。** accepted_id 和 retired_id 跨 Alt0、DeInit、重枚举及本机 STOP 保留。UsbTask 到 A2 终结确认提交前不接收下一次 Submit，查询不是消费协议，也不会清除旧记录。accepted_first_fault 只关联当前 accepted_id，后续成功取消或 STOP 不覆盖它。独立的 EOF 计数仅用于实板报告。调用者不暴露 Media 地址或物理 buffer_id。
- **允许归还的条件。** UsbTask 已保存成功提交对应的 expected_id，且查询成功、accepted_id 与 retired_id 都等于 expected_id、原因是明确终结，才调用 A2 `UsbService_ReleaseFrame()`。失败或不明确就保留 READING、旧身份和首错。唯有从未被 UVC 接受的 View，才可在确认 Submit 返回 BUSY/ERROR 或关闭本地需求后由 UsbTask 直接归还。不存在定时强制归还。

候选生产修改仅限 `CM7/Service/usb_uvc.h`、`CM7/Service/usb_uvc_class.c` 和 `CM7/ApplicationV3/Services/USB/usb_service.c`，再单独接入测试配置。沿用当前 Payload、Platform 和 BSP 公开接口。A1/A2 账本、RTOS、ST Core 均无需修改。

## 3. 申请批准的 STOP/FAULT 顺序

1. 在原 UsbTask 轮次先关闭新申请和提交，再推进已登记的旧帧。正常 ACTIVE 在 `can_submit` 成立后用 A2 取只读 View，核对 Raw 格式和 38,400 B 连续数据后调用 Submit。已成功的本地提交被识别为预期占用，未知 Class 占用仍报错。
2. 正常运行复用原 Process、SOF 和 IN completion；健康 Suspend 保留身份并暂停正常进包工作，真实 Resume/CONFIGURED 后继续。明确 STOP 则允许走原 Cancel/Process 能推进的取消分支，不能将 Suspend/Reset 事件直接等同于读者退出。
3. 将旧帧 Cancel/Process/只读证据查询放到 `UsbService_StopDevice()` 的最终状态门禁之前。在 QUIESCING 或 FAULT 中继续运行，证据匹配才能 Release。继续由 A2 发送 RETURN、等 RETURN_ACK 实际消费并提交 ACK_CONSUMED。之后执行原 Device STOP / 端点复核，原命令结果语义保持。
4. **单独审批的异常恢复选项。** Class/Platform 清理交错可能留下 Class 还认为 EP1 已开、Platform 已确认关端点，随后 Abort 返回 INVALID_STATE。在显式 RECOVER 中，如需允许原 `USB_Device_Stop()` 先执行受控硬件停止和 DeInit，仍保留 A2 的读者身份，随后必须拿到同 ID 的 Class 退休证据才能 Return。即使 USB_Device_Stop 返回 OK 也不能自行当作归还。硬件/类仍无法证实时保持故障和借用，不开放 READY，也不自动重启。
5. Camera STOP 关闭新的借出，消费既有 Return 和 ACK。健康链路上的旧帧允许完成后归还。Camera 单独 STOP 遇 USB 挂起或读者不能退出时，按原有界等待报告失败，租约保留；明确 USB STOP/RECOVER 后才可继续关闭。USB 独立 STOP 不触发 Camera 全局 STOP。

## 4. 独立测试配置与后续验收

- 建议给原 CM7 测试构建增加单独且默认关闭的 Raw profile，明确拒绝与产品 MJPEG、现有单 Service 板测场景混用。使用现有 ControlTask 与既有 START/STOP 命令，受控地先 Camera 后 USB，停止顺序先 USB 后 Camera。产品提交保持 `APP_VIDEO_MJPEG_MODE=1`、MJPEG 320×240 / 25 FPS，不改变产品 BOOT。测试 profile 指定 YUY2 160×120 / 10 FPS，38,400 B。

- 软件专项用真实 UVC Class/Payload 与可控端点，覆盖未 Commit/Alt1、Submit BUSY/ERROR、匹配末包 EOF、错/迟包、Cancel 登记后仍持有、Abort/Close 失败转重试、正常 Suspend/Resume、挂起时明确 STOP、有持帧的 Camera STOP、Alt0/Reset/DeConfig、Class 解绑到重新分配之间的证据、编号不回绕与首错冻结。判据同时核对旧源不被重借、匹配帧最多一次 RETURN 以及三条 A2 运输背压边界。
