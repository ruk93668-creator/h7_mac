## 启动与所有权

1. CM7 原 `main.c` 先调用 `App_TasksCreate()`。应用建立事件绑定和静态消息通道，创建并登记五个任务。创建服务的静态清单顺序为 Camera、USB、Storage，随后创建 Control、IPC。任务此时尚未调度。
2. `Framework_InitRuntime()` 运行 `App_Init()`，准备共享配置并建立 Record 槽。主流程将 Framework 结果提交给 `App_TasksRecordInitialization()`，再按原入口启动调度。任务创建或 Framework 失败时，原 BOOT 屏障不放行。
3. Control 先订阅启动通道，再释放 BOOT。三个服务在自己的任务中各执行一次初始化。成功会发布实际只读服务实例，失败会公开具体错误。Record 可打开与启动报告已发送是两个独立事实。
4. Control 只消费专用 `APP_CHANNEL_STARTUP`。报告须匹配静态服务身份、命令编号零、ACK/FAULT 语义及真实 Record 结果。全部三个结果成功才发布整体 `SYS_OK`。重复结果被拒绝计数，独立业务通道中的消息仍在原队列中。
5. Control 自准备放行 BOOT 起计 1000 ms，按消费时刻判断截止。已观察到的首次失败会被冻结。截止时缺少确认的服务会形成 `SYS_ERR_TIMEOUT`，晚到成功仍可用于维护 Record，但无法改写启动结论。队列背压时每个服务最多尝试 11 次，每轮保存相同结果。通知只提示，定时检查间隔最多 100 ms。

## Queue Pool、Record 与 Event Loop

- Queue 池有六个四项宽槽和三个单项信号槽。原五条通道和启动通道各占一个宽槽，三项 Record 各占一项信号槽。消息仍以 FreeRTOS 的值复制交付。发送成功后，通知失败不会改变入队结果。
- 池按代次验证句柄。短 PRIMASK 临界区保护固定槽和在途操作数，阻塞收发留给 FreeRTOS。Free 拒绝有订阅、在途访问或未消费消息的槽。ISR 仅可通过专用零等待接口访问，且须符合 FreeRTOS 的外设 IRQ 优先级条件。
- Record 的就绪信号使用非破坏性 `xQueuePeek()`，多个等待者可依次看到同一发布。等待者和已发票据均拦截销毁，票据匹配打开任务、服务、实例及编号。槽以固定票据数组表达持有关系。打开只授予读取已发布对象的能力。
- 服务各持有自己的事件循环。V3.1A 真实订阅是 Control 的启动队列，三个业务服务保留 BOOT 等待。回调从真实队列取得数据，合并通知或晚到通知不会消费额外数据。有订阅时等待最长 100 ms，未订阅时可阻塞等待新事件。
