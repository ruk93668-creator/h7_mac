# V3.1C-R2-C USB Suspend 误判修复

输入基线为 `4a8e95b96b0fe9481de22d00873d712c96136942`。实板首错截图记录 `SET_CONFIGURATION(1)` 于 1304 ms 使 USB 进入 CONFIGURED，随后 2324 ms 的 Suspend 使 Core 转为 SUSPENDED、旧状态为 CONFIGURED。首错处 `started=1`、`stop_required=0`、Core 返回 0。原 Service 仍以配置条件消失为由锁存 `SYS_ERR_IO`。旧实板循环失败和成功 STOP 证据保留。

## 最小修复

`USB_Device_ReadLinkState()` 在一个短 PRIMASK 临界区中复制五项 Core 字段，按同一采样点返回原 CONFIGURED 判据，然后恢复调用者的中断状态。正式路径只复制轻量状态。R2-C 测试路径沿用同一内部读取逻辑，同时保留既有八条事件诊断。

`AppV3_UsbAdvance()` 只在 ACTIVE 时将以下状态视为健康挂起：当前 SUSPENDED、挂起前 CONFIGURED、已启动、无待 STOP 义务、Core 无错误。此时保持 ACTIVE，清除 CONFIGURED 标志，保留既有资源和持有事实，暂停 UVC 观察推进，等待重新观察到 CONFIGURED。START 完成仍要求实际 CONFIGURED。显式 STOP 仍走原 USB 停止和帧清理路径。

Reset、Disconnect、SET_CONFIGURATION(0)、从未配置状态进入 Suspend、待 STOP 义务和真实 Core 错误仍走原 FAULT 路径。设备采样时已有的错误在 ACTIVE 下保留。没有新增 Service 命令、生命周期状态或自动恢复，ST Library 的处理保持原样。

原 ID61 的行为断言继续要求真实失去配置后即使 STOP 成功也判失败。其夹具现在明确注入 DEFAULT，避免把失联负对照建模为本轮已经确认合法的健康 Suspend。ID63 独立锁定新的健康状态语义。

实板复测仍为 NOT_RUN，R2-C 尚未通过。五分钟稳定性检查允许健康 Suspend，同时必须记录恢复后重新 CONFIGURED 和最后的安全 STOP。软件时间推进不能代替实板持续运行。
