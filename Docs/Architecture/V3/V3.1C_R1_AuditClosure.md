冻结生产源码为 `ce03ddbf05ed94c821643cbce807e86f245962a0`。生产修复为 `c63288a401f71400c51f991a9e1f36873251ce6a`，构建及专项对应的源码与测试树为 `0c8ca6083722dd7c8369885835aa076f0a5c56f8`。

## USB 注册失败的根因

1. [UsbService_BeginDevice](../../../CM7/ApplicationV3/Services/USB/usb_service.c#L101) 先调用 `USB_UVC_Configure()` 准备描述符，再调用 [USB_UVC_Register](../../../CM7/Service/usb_uvc_class.c#L245)。原实现仅在后续 `USB_Device_Start()` 返回后登记 Service 的停止义务，注册失败会越过登记点。
2. [Usb_RegisterClass](../../../CM7/Platform/usb_device.c#L1436) 通过 `Usb_PlanEndpoints()` 配置 BSP 端点及 FIFO。规划返回 IO 或 TIMEOUT 时，USB Core 可以留下 `s_stop_required=true`，即使 USB 从未启动、未配置且 UVC Class 尚未注册。
3. Service 未登记停止义务时，[UsbService_StopDevice](../../../CM7/ApplicationV3/Services/USB/usb_service.c#L167) 直接成功返回，随后启动回退按成功清理处理并报告 `READY`。负对照观察到 Core 停止义务仍在且实际 STOP 调用为零。

描述符配置成功后，Service 现在在首次可能改变 Core 的调用前登记清理义务，注册和启动共用原有 STOP 入口。纯描述符配置失败仍可直接回退，Core 上干净状态的空 STOP 仍由 [Usb_StopDevice](../../../CM7/Platform/usb_device.c#L1537) 自行确认。BUSY 保持排空等待，IO 或 TIMEOUT 保持 FAULT，只有原停止及端点核验成功才能回到 READY。START 终结保留注册原错，失败 RECOVER 报告本次错误并继续保留首错，成功 RECOVER 同样保留该首错供核验。底层 USB、任务及 IPC 均无源码变更。

## R2 受控真实命令入口提案

默认固件在 BOOT 就绪后由现有 Control 执行业务结果消费，当前没有主动提交真实硬件命令的入口。R2 建议在可审查的测试构建中为现有 Control 循环增加一个默认关闭的调试器命令槽。仅在 BOOT 成功、手工授权且槽空时受理。命令字段为版本、单调序号、Service 和操作；写入完整载荷后最后发布有效位，Control 先复制完整快照再执行白名单和重放检查。白名单仅允许指定 Service 的 START、STOP、HARDWARE_QUERY 和 RECOVER。验证分批进行，SD 使用只读挂载、容量查询和卸载。

Control 仅调用现有 `CameraService_Request`、`UsbService_Request` 或 `StorageService_Request`，硬件仍由对应 Service Task 执行。区分命令被接收、入队和真实完成，使用现有业务消费链匹配 Service、Requester 与 Command ID。固定槽仅允许一条在途命令，提交 BUSY 保留原序号，终结记录需经调试器显式确认方可复用。超时只记录等待超时，保留原事务，不以超时宣告设备停止。此提案待人工批准，默认 BOOT 不启动设备，无新增任务、串口或 IPC 协议。
