## B1～B4 所有权、请求与完成

| Service | 固定线程入口 | 私有模拟状态 | 私有队列与事件循环 |
| --- | --- | --- | --- |
| Camera | `AppV3_CameraRun` | 模拟运行位、图样参数 1～255、只读采集配置 | Camera 独占 |
| USB | `AppV3_UsbRun` | 模拟运行位、包数限制参数 1～1024、只读输出配置 | Usb 独占 |
| Storage | `AppV3_StorageRun` | 模拟运行位、抽样分频参数 1～64、只读 Storage 配置 | Storage 独占 |

每个 Context 包含私有命令队列、Event Loop、按调用任务记录的命令编号高水位、完成序号及允许一条待交付结果的存储。该待交付结果用于背压重试。另有独立的 8 B 只读入口句柄，由发布者在 Record 可见前填入。其他任务不访问服务私有 Context。三个公开 API 分别为 `CameraService_Request()`、`UsbService_Request()`、`StorageService_Request()`；异步 QUERY 的完成事件携带模拟状态和参数。

1. Registry 创建三个实际线程入口，原 BOOT 放行后各所属任务校验配置、分配并订阅自己的队列，再发布 Record。任一步失败均不可取得该服务可用入口。Control 确认三项启动结果全部成功后才开放请求提交。
2. 调用任务必须是已登记的普通任务，当前任务不能向自身服务提交。API 以零等待打开 Record，核验固定实例身份，在引用存续期间复制命令进队列，再关闭引用。非零 `command_id` 与任务身份组成面向每个 Service 的命令身份。同一来源的编号须严格递增。返回 `SYS_OK` 说明消息已入队，满队列返回 `SYS_ERR_BUSY`，重试可使用同一未入队编号。
3. 服务从订阅队列取走命令并通过身份和编号检查后进入具体 Handler。Handler 分别处理模拟启动、停止、参数修改、查询和模拟失败。真正的处理开始点在取件及校验之后，公开协议提供终结事件，没有单独的 Started 回执。重复、迟到、无效操作或参数产生 FAULT，禁止重复执行之前的操作。
4. 业务成功使用 ACK，失败使用 FAULT。业务事件按值保存来源、请求任务、命令编号、序号、执行结果、模拟运行位和参数。Control 依据专用标记解码原 52 B 的 `AppMessage_t`。此编码仅用于模拟完成，数据指针始终为空，类型和消息 ABI 保持原样。
5. Control 队列满时服务保留一条已完成结果，并在后续循环重新提交；旧结果入队前不取新命令。Control 实际出队后才进入 PubSub。队列通知无效时，原定时回查仍能推进。启动报告走 `APP_CHANNEL_STARTUP`，业务结果走原 `APP_CHANNEL_CONTROL`。

三条私有 Queue 各有 4 × 16 B 有效负载，使用 R1 已计入 Map 的 3 个宽槽，Queue Pool 总计仍为 2940 B。系统服务全部成功初始化后，9 条宽槽和 3 条短信号槽均分配完毕。新增私有队列没有引入其他活动命令入口。保留 `APP_CHANNEL_CAMERA_COMMAND`、`APP_CHANNEL_USB_COMMAND` 以及 Camera↔USB 的历史路由，供后续兼容性审核。V3.1B 只有私有队列执行模拟操作。

## B5 Control 消费与 PubSub

- 三个固定订阅槽支持按单项服务或全部订阅。只有 Control 能建立、撤销和使用订阅。票据不回绕，重复订阅被拒，旧票据不能撤销复用槽中的新订阅。
- Control 每轮消费最多四项。未知或非法消息产生 `SYS_ERR_PROTOCOL` 并记录最后拒绝的消息类型、来源和命令编号。业务诊断不保存未知消息携带的指针。
- 消费后创建本次事件对象，同步调用 Control 所属的订阅者。参数仅在回调期间有效，异步使用者须自己复制。回调不得阻塞等待发布者，也不能递归进入消费。执行在临界区之外。
- 发布前记录订阅票据。回调内撤销可立即生效，被撤销的后续回调不再访问其上下文。同一轮新加入的订阅从下一条事件开始接收。上下文由 Control 所有，撤销后方可释放。
- 回调失败与 Service 结果分别保存。其他订阅继续执行，成功的业务 ACK 不因回调错误改为失败。现有固件还没有注册外部业务客户端，专项通过真实 API 注册和发送。
