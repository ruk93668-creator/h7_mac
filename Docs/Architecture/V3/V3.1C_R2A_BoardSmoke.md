# Application V3.1C-R2-A 实板测试入口与软件验收

生产基线为 `11f98ef445f2cd72465f69392dc7070a4d6478f6`，验证源码为 `92dbc5edf5ef5fc9e112af6ca5975db4bcfe9c03`。本轮运行真实 Service 软件及可控硬件夹具，并重建正式和测试固件。烧录与实板观测尚未执行。

## 入口及执行顺序

[board_smoke.h](../../../CM7/ApplicationV3/Tasks/board_smoke.h) 默认选择 OFF。[service_tasks.c](../../../CM7/ApplicationV3/Tasks/service_tasks.c) 在 BOOT 成功且 Control 已完成当轮业务队列消费之后推进测试。只有被选中的 Service Request 会被测试钩子引用。流程固定为 `START → HARDWARE_QUERY → STOP → HARDWARE_QUERY`，硬件操作仍由原 Service Task 执行。RECOVER 保持原 API，留给后续经批准的异常验收，本轮脚本没有自动恢复动作。

Control 先订阅现有 PubSub，再提交命令。回调只复制当前命令的值结果，核对 Service、Control 请求者、真实硬件结果标记和命令号。同一步最多保存一个结果，未成功入队的 BUSY 用原编号重试。四个命令编号从 `0x7B530001` 到 `0x7B530004`。每步的提交和完成等待共用 10 s 期限。下个命令在回调返回且当轮消费结束后提交。完成或失败后撤销订阅，Keil Watch 保留此前已记录的原始结果。

`COMPLETE` 表示收到四个匹配结果，前两步返回 ACTIVE，后两步返回 READY。故障、状态不符或超时都会停止脚本。超时仅表达测试等待期限已过，原命令仍可能在其 Service 内执行。脚本不会据此发第二条命令、主动 STOP、宣告设备停止或释放任何资源。

## 构建配置与操作步骤

1. 使用原 `MDK-ARM/h7_mac.uvprojx` 的 `h7_mac_CM7` Target。正式构建保持默认值 `0`。实板获批后，可临时在 `service_tasks.c` 的 Keil 文件级 C/C++ Define 设一个值，或直接使用本轮已保存的对应 AXF。
2. 选择 `APP_V3_BOARD_SMOKE=1` 测 Camera、`=2` 测 USB、`=3` 测 Storage。构建与烧录均逐场景执行。切换场景前完成当前板卡验收。USB 场景在复位前准备独立 UVC 数据连接。本轮三个测试 AXF 已分别保存，原 Keil 输出目录最后重建为默认配置。若本地临时通过文件级选项选择测试，结束后去掉该定义并重建产品固件。
3. 测试镜像复位且 BOOT 成功时所选 START 自动提交。在 Keil Watch 添加 `g_app_v3_board_smoke`。让板卡连续运行到终态后暂停读取，避免断点影响 USB 枚举、时限和 RTOS 调度。查看 `state`、`step`、`received`、`result`，再展开 `events[0..received-1]` 记录命令编号、序号、真实结果、`hardware.state`、`first_fault`、`flags`、`primary` 和 `detail`。USB 枚举和真实外设状态需要独立实板记录。
4. 如出现 `FAILED` 或 `TIMED_OUT`，先保存 Watch 与外设证据。跳过下一设备及自动重跑，按后续批准的 R2 故障步骤处理仍可能活动的 Service。

| 场景 | 独立实板证据 | 本轮 |
| --- | --- | --- |
| Camera | 验证 OV5640 工作与首帧。START 的 `FRAME_SEEN` 位 `0x01` 在有效帧成功归还后才置位，`FRAME_HELD` 位 `0x02` 应清。STOP 查看 `MEDIA_STOPPED` 位 `0x04` 和本采集实例的成功停止事实，核对 DCMI/DMA 及无待归还 | NOT_RUN |
| USB | 在 Windows 核对 UVC 设备完成枚举，START/QUERY 的 CONFIGURED 位 `0x01` 应置位。STOP 检查 VIDEO_QUIET 位 `0x02` 已置位，端点 `0x81` 不忙且未打开，设备未配置。本场景不发视频帧 | NOT_RUN |
| Storage | 既有 START 调用 `StorageFS_Mount(false, partition)`。核对只读卷、FATFS 租约及 QUERY 的总容量和可用容量，单位为 512 B。STOP 须有已卸载、无文件、FATFS 租约解除和清理成功，随后 QUERY 可只报告卡在位。禁止写卡 | NOT_RUN |
| 运行期 | 任务响应和任务栈高水位由实板采集。反复启停、断连、拔卡、RECOVER 失败及资源遗留属于后续验收 | NOT_RUN |

## 软件验证

使用 ARMCC5 V5.06 update 7 build 960 编译、链接，并由现有 Cortex-M 执行器运行。默认构建 O0/O2 各 53/53，保留原 49 项和 R1 四项。单场景构建 Camera、USB、Storage 的 O0/O2 各自均为 5/5，合计 30 次专项通过。夹具复用真实 Control 入口、Request、FreeRTOS Queue、Service 操作和 PubSub，设备事实由夹具注入。

| 测试 ID | 断言 |
| --- | --- |
| 53 | 单独的四步运行，只有所选服务启动，核验帧归还、USB STOP 或只读挂载及卸载 |
| 54 | 首次队列拒绝并丢失通知。重试沿用原编号，错误服务、模拟结果和错误命令号不能推进 |
| 55 | START 终结迟到。测试报告超时，未发 STOP，迟到结果不改变测试终态 |
| 56 | 真实 STOP 路径的底层 IO 注入，保留原命令结果及首错，脚本停在 FAULT |
| 57 | 未完成 BOOT，超时后钩子保持 IDLE，三个设备均未启动 |

测试命令为 `python Tests/ApplicationV3/run_tests.py <新输出目录> --board-smoke <off|camera|usb|storage>`，沿用原 Cortex-M Python 夹具依赖和 ARMCC5 安装。专项输出位于 `output/ApplicationV3/V3.1C/R2A/Software-*/`。包含实际退出码、源编译命令和 `results.json`。

## Keil 构建和内存

原 CM7/CM4 默认固件完整 Rebuild 均为 0 Error、0 Warning。三个独立测试配置的 CM7 Rebuild 同样为 0 Error、0 Warning。构建测试时仅临时选择新头文件中的场景，保存实际编译头后按字节恢复默认值并重建默认固件。两份用户 Keil 配置前后 SHA256 相同。CM4 HEX 与 R1 冻结版逐字节一致，SHA256 为 `3030484c03d4983a192be39142dce7b6dfdb8e6c93a49e1f8285ee846540fb17`。

| Code | 121,038 B | 121,042 B | 123,126 B |
| RO / RW / ZI | 3,318 / 1,276 / 100,180 B | 3,318 / 1,276 / 100,180 B | 3,350 / 1,284 / 100,364 B |
| Flash，Code + RO + RW | 125,632 B | 125,636 B | 127,760 B |

默认 Map 不含测试钩子或诊断对象。默认 Code 增加 4 B，反汇编确认 `AppV3_ControlRun` 中两个原有断言行号由短立即数指令改为宽立即数指令。测试配置相对默认增加 Flash 2,124 B、DTCM 192 B，Watch 对象 192 B，另有票据和 Tick 各 4 B，净增量以整个 DTCM 链接区为准。链接器调用链估算不包含不可追踪路径，不能替代 3,072 B Control 静态栈的实板高水位。任务栈配置、优先级、队列深度与 ABI 保持不变。ARMCC5 断言 `AppMessage_t` 52 B、`IpcApplicationStatus_t` 80 B、`AppV3ServiceCommand_t` 16 B。

`output/ApplicationV3/V3.1C/R2A/Build-Default/` 保存默认双核日志、实际 AXF、Map 和 CM4 HEX，`Build-CAMERA/`、`Build-USB/`、`Build-STORAGE/` 各自保存该场景 CM7 证据。产品 CM7 Map 和三个测试 Map 的符号关系、内存数据、SHA256 及 Keil 原始哈希在 `verification.json`。完整源码差异见 `V3.1C_R2A.diff`。
