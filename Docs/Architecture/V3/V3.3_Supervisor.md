# V3.3 ControlTask 业务协调

在原 ControlTask 消费既有 Business 结果后调用 Supervisor。系统 BOOT 仍只完成软件初始化，硬件启停由 Control 所属代码明确请求。Supervisor 不拥有硬件、原帧、队列或新任务。状态快照包含已确认的活动位、仍需确认退出的位、在途命令号与各模块最近匹配结果。

`AppV3Supervisor_Set(mask, file_number)` 接受 Camera、USB 与录像三种目标，USB 或录像自动纳入 Camera 依赖。原 Service 的 ACTIVE 是启动依据。全停时先关 Storage/USB，最后停止 Camera。仅退出一路时保持仍被另一路引用的 Camera。失败的步骤保留首错和原业务结果，未证明退出的消费者阻止 Camera 停止。随后可显式提交 `Recover(component)`。失败后下一次由调用者选择清理计划；协调器没有自动重启硬件。

`Query(component)` 通过该 Service 原有只读业务命令刷新快照，包括 Storage 写帧和空间值。`Read()` 返回最近一次确认的状态；后端自主运行变化需经 Query 刷新。拒绝不在固定依赖表内的位。本阶段没有注册 Ethernet 行，预留由获准网络契约补入的依赖位置，也没有改动 IPC 或创建外部命令通道。

同一时刻只提交一条硬件命令。Control 以真实业务结果、来源、请求者及命令号匹配。队列满只重试未入队请求，入队后的超时保留原事务，只接收同身份迟到结果；不会跳过依赖、伪造归还或运行另一条清理命令。

ARMCC5 ID92–95 在 O0、O2 各通过 4/4，覆盖正常启动、独立关闭 USB、状态查询、全停、USB 启动失败、迟到结果和 USB STOP 失败后显式恢复。默认套件各 73/73。A1、A2、A3 与本地 A4.1 软件回归通过。产品 CM7 与 CM4 完整 Rebuild 均为 0 Error、0 Warning，CM4 HEX 与冻结版一致，静态栈与优先级不变。完整证据在 `output/ApplicationV3/V3.3/`，实板和运行期高水位仍为 NOT_RUN。
