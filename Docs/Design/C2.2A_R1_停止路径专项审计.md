# C2.2A PR #6 — R1停止路径专项审计与测试设计

## 1. 基线、范围与结论

- 审计生产源码：aa38870a0532bc86420f896bfb1dbf44edc88edd，分支codex/stage-C2-2A-consumer-qualification-core，PR #6。
- main基线：182c84e7334f0a62d96f1d3109b0d7fb8efb8158；提交文档前已远端核对PR分支仍为aa38870、main仍为182c84e。
- 本轮只读源码并新增本文，不修改生产、测试或工程配置，不运行测试或编译，不创建新分支、不修改main、不合并PR。
- output/在开始时已未跟踪，原样保留。

结论：目前CameraTask是唯一任务侧停止执行者，但不是“每轮仅一个停止推进入口”。原故障处理、App_CameraRun自动停传感器、FinishRound及未来资格停止回调是不同的串行调用点。相同任务不等于每轮只提交一次底层停止。

必须分开表达：

1. **当前新增资格停止回调不可达**：CameraTask没有调用资格入口，生产资源表idle/released为空，STOP_IF_IDLE也过不了idle门控。不能宣称当前固件已经因资格回调产生双Stop。
2. **当前旧故障路径确有同轮重复停止调用的可构造控制流**：第一次BSP停止失败时，轮末能够再次进入BSP/HAL；启动失败清理也可能增加同轮尝试。这些路径在c6d2bed之前已经存在，不是本PR新增。
3. **未来直接叠加资格Process存在双推进风险**：资格回调与FinishRound均调用App_CameraStop并写同一组停止字段；BUSY/失败会保留stopping，使同轮后续入口继续推进。C2.2B接入前必须确定唯一普通停止推进口。
4. **重复API调用不等于重复硬件操作**：Media NONE/IDLE、DRAINING以及Device READY分别有短路保护；一次成功停止后，后续调用经常不会再次执行BSP/HAL或传感器寄存器写。

上述“可构造控制流”是源码结论，不是本轮软件执行或实板复现结果。本文所有新增测试均为待实施设计。

## 2. 五个重点函数及下层边界

| 函数 | 源码位置 | 确认事实 |
|---|---|---|
| App_CameraQualificationStop | CM7/Application/app_camera.c:491–507 | 置stopping；调用App_CameraStop；成功后查Bridge；完整成功才清running/stopping并记录停止确认；BUSY保留待停，其他错误保留fault |
| App_CameraFinishRound | 同文件:301–350 | stopping时再次调用App_CameraStop，成功后查Bridge；完整成功才清标志；只处理旧stop_command ACK，不提交生命周期回复 |
| App_CameraStop | 同文件:99–119 | CameraCapture_Stop→IsStopped→Device READY短路或Device_Stop；Media返回OK不直接等于完整停止 |
| CameraCapture_Stop | CM7/Media/Src/camera_capture.c:684–795 | 正常持帧BUSY；ERROR可先保护性停硬件；DRAINING保留引用；完整NONE/IDLE幂等返回 |
| Device_Stop | CM7/Device/Src/device.c:237–282 | 注册身份核对；只允许RUNNING；调用具体stop前置BUSY；成功置READY，任何失败置ERROR |

补充链路：

- BSP_DCMI_Stop：CM7/BSP/bsp_dcmi.c:590–676。每次通过入口检查后都会进入HAL_DCMI_Stop、硬件停止等待及HAL恢复；s_control_busy只防正在执行的重入，返回前会清除，不能防同轮稍后的第二次调用。
- 实际传感器停止：Device_Stop→Ov5640_Stop（CM7/Device/Src/ov5640_device.c:182–194）→OV5640_Stop（CM7/Device/Components/OV5640/ov5640.c:2173–2178）→写SYSTEM_CTROL0为0x42。
- BSP停止成功不仅检查HAL返回，还检查DMA EN及DCMI CAPTURE/ENABLE清零（bsp_dcmi.c:1439–1449），并恢复HAL（1453–1492）。本轮没有测量这些操作耗时。
- 错误ISR只锁存错误并通知CameraTask，不在ISR调用Stop（bsp_dcmi.c:1362–1384）。本轮问题是串行多入口，不是已证实的跨任务并发停止。

## 3. 当前实际可达调用链

### 3.1 一轮的精确定义

“一轮”指一次CameraTask_Process(events)调用（camera_task.c:112–136），包括本轮命令处理、Media推进、Bridge及轮末收尾；不是一个Tick、一个SOF或两次任务唤醒之间的固定毫秒段。任务在中间被抢占后恢复，仍属于同一轮。

```text
CameraTask_Run
  → CameraTask_Process
      → CameraTask_Reply
      → 最多一条旧控制命令
          START → App_CameraStartResource → App_CameraInitStream
                → App_CameraStart → 启动失败时App_CameraStop
          STOP  → 设置stopping/stop_command，不立刻停硬件
      → App_CameraProcess
          → App_CameraRun
              → CameraCapture_Process
                  → 既有ERROR / 新采集错误 / JPEG错误时CameraCapture_Stop
              → 若Media完整停止且Device仍RUNNING：App_CameraStop
          → 识别采集故障，更新fault/running/stopping
      → App_UvcBridgeCameraProcess(enabled)
          → Storage归还、USB Return/ACK及原帧实际释放
      → App_CameraFinishRound
          → stopping时App_CameraStop
          → 成功后Bridge Idle确认
      → CameraTask_Reply
```

入口位置：camera_task.c:124–135；启动失败回退app_camera.c:204–210；自动停止app_camera.c:123–131；错误识别272–289；轮末301–329。

Bridge推进仍在Media和Finish之间，包含Storage归还（app_uvc_bridge.c:148）以及USB归还/回复（150–206）。所以本轮前半段看到持帧，后半段已经归还是合法进展，不能简单把第二次调用一律当成重复硬件提交。

### 3.2 当前新增资格路径为何不可达

- CameraTask的实际循环没有App_CameraQualificationPrepare/Receive/Process/Flush调用（camera_task.c:112–136）。
- App_CameraQualificationProcess只定义在app_camera_qualification.c:519–524，现有USB/Storage/Control业务没有接入。
- s_qualification_ops的released、idle均为NULL（app_camera.c:510–515）。即使未来只接入运输而尚未提供证明，Qual_Execute在app_camera_qualification.c:363–366会终结BUSY，不能到373行ops->stop。
- 未初始化核心也不能绕过这些条件；公开入口仍检查Camera所属任务和ISR（app_camera_qualification.c:491–497）。

因此，“资格回调+FinishRound导致当前固件双Stop”没有当前可达依据。既有独立测试可以替换证明回调，但那是测试配置，不是生产可达性。

## 4. 重复调用与真实停止的分层判断

### 4.1 幂等与排空保护

| Media/Device状态 | 再次调用结果 | 是否再次进入底层 |
|---|---|---|
| Media NONE+IDLE | CameraCapture_Stop返回OK（694–698） | 不调用BSP |
| Stream CAPTURING且有借帧 | BUSY（727–749） | 不调用BSP，不回收帧 |
| JPEG DRAINING且仍有任一路引用 | BUSY（705–716） | 不调用BSP，不再次OnStopped |
| JPEG DRAINING且引用已清 | 转NONE/IDLE返回OK（707–713） | 不调用BSP |
| Media READY单帧待释放 | BUSY（719–721） | 不调用BSP；仍须原Release路径 |
| Media ERROR且底层上次失败 | 可再次到755行BSP_DCMI_Stop | 可能再次HAL停止/恢复 |
| Media已完整停止、Device READY | App_CameraStop返回OK（116–117） | 不调用Device_Stop或传感器stop |
| Device BUSY | Device_Stop返回BUSY（260–261） | 不调用具体生命周期 |
| Device ERROR | Device_Stop返回INVALID_STATE（264–265） | 不再次调用传感器stop；也不会自行恢复 |

ERROR且有引用时，Media允许先停硬件，成功后进入DRAINING并返回OK（780–788）。App_CameraStop随后用IsStopped拒绝把它当成整体完成，因此不会提前Device_Stop。

CameraMjpegFifo_OnStopped只在BSP确认成功后调用（camera_capture.c:768–771）；它保留仍有引用的SEALED块（camera_mjpeg_fifo.c:453–472）。HasLoan同时检查USB和SD（441–449）。没有发现这条Stop路径仅凭stopping就强清外部引用。

### 4.2 可由源码逐步推演的代表路径

以下计数仅限表中前置和返回序列，不宣称是所有嵌套路径的全局最大值；也不把HAL函数调用次数当作某条寄存器写次数。

| 场景与前置 | 一轮内可见调用 | 真实BSP/传感器情况 |
|---|---|---|
| 正常旧STOP、无租约、Bridge空闲、底层成功 | Finish调用App_Stop一次 | BSP一次，Device生命周期一次 |
| 正常旧STOP仍持帧且Bridge未归还 | Finish→Media_Stop BUSY | BSP零次，Device零次 |
| 采集ERROR、无引用、首次BSP成功、Device成功 | Media保护Stop；App_Run→App_Stop；Finish→App_Stop | Media_Stop可三次，但BSP仅一次；真实Device stop一次，末次READY短路 |
| 采集ERROR、有引用、保护Stop成功，Bridge本轮仍未归还 | 保护Stop进入DRAINING；Finish再查Stop | Media_Stop两次，BSP一次，Device零次 |
| 同上，Bridge本轮完成最后归还 | Finish可继续传感器停止 | 不重复BSP；实际归还后才Device_Stop |
| 采集ERROR，保护性BSP停止失败且模式/ERROR保留 | Media_Process一次；Finish再次App_Stop→Media_Stop | 同轮可两次BSP/HAL停止；不是成功后重复，而是失败后即时再试 |
| 本轮START失败清理BSP也失败，随后Media错误处理和Finish都失败 | 启动回退、Media_Process、Finish分别进入Stop | 可构造同轮三次BSP尝试；属于原路径重试叠加 |
| 正常Stop已完成Media/Device，但Bridge仍不空闲 | 本轮保留stopping；下一轮Finish再次App_Stop | 下一轮NONE/IDLE及READY短路，不重新提交BSP或传感器停止 |

即使DMA/DCMI停机位已经清零，HAL恢复或HAL_Stop返回检查失败仍可使Media保留ERROR；因此“本次Stop失败”不能反推“硬件一定还在运行”，再次进入BSP仍可能重复HAL停止/重建。

原路径在CameraCapture_Process:527–534、556–563、607–611及App_CameraRun:129–131有前半轮停止；Finish:309是后半轮入口。BSP失败会保留ERROR（camera_capture.c:757–765），没有round_id或“本轮已尝试”门控，所以以上失败重试路径成立。

## 5. 未来C2.2B直接接入时的风险

### 5.1 两个普通停止执行点

未来只有在绑定真实idle证据、完成资格/引用前置后，才可能执行：

```text
App_CameraQualificationProcess
  → App_QualificationProcess
    → Qual_Execute(STOP_IF_IDLE)
      → App_CameraQualificationStop
        → stopping=true
        → App_CameraStop
        → Bridge Idle
```

如果把该Process放到同轮FinishRound之前，回调BUSY或失败后stopping仍为true，后面的FinishRound会再次执行App_CameraStop。原App_CameraProcess中的保护/自动停止也可能参与。

- 新回调完全成功：它会清stopping，后面的Finish通常跳过，没有必然双Stop。
- 新回调返回BUSY且已经安全停完硬件、仅Bridge待确认：Finish可能再调用上层Stop，但通常被NONE/IDLE及READY挡住，不重复硬件停止。
- 新回调底层停止失败：ERROR仍在，随后原Media_Process/Finish可能再次下发BSP。若采用“资格Process→原CameraProcess→Bridge→Finish”的示例顺序，失败持续时可构造三个调用点；若只插入Bridge后、Finish前，则至少存在两个调用点。
- 若插在Finish之后，只避开这两个入口在该轮的先后关系；不能据此证明原Media保护Stop和下一轮Finish已收敛。

C2.2B尚未确定插入位置，本审计不会把上述假设顺序描述成当前代码。

### 5.2 不是两个消费者就一定两次停止

App_QualificationProcess确实按两个方向循环（397–431），但Qual_OtherWork（229–244）会检查另一方向工作、资格、候选及未稳定回复。第一次STOP等待BUSY时，另一方向不能因此同时执行另一个普通硬件Stop；第一次成功关闭session后，新请求也受会话校验。因此问题重点是“资格资源回调与旧轮末入口叠加”，不能错误简化为USB/Storage各停一次硬件。

### 5.3 状态与完成语义

| 状态/结果 | 审计判断 |
|---|---|
| running仍true、stopping=true、硬件可能已停 | Bridge未空时可出现；CanOfferFrame仍false（app_camera.c:295–297），ResourceState优先返回STOPPING/FAULT_DRAINING（469–470），不是必然误开新帧 |
| 资格回调BUSY，Finish后来成功 | 硬件/Bridge可能已完成，但生命周期工作尚未终结；Finish不调用RxComplete。下一轮Core可观察STOPPED_CONFIRMED后固定原请求，不应再次执行已完成硬件动作 |
| 资格Stop终结失败，Finish后来成功 | 原失败回复必须保持，不能改成成功；resource_stop_confirmed与session_closed不由同一入口推进。需明确失败后的新STOP/会话关闭策略，不能自动重置Replay或借新QUERY假定旧事务成功 |
| Device stop回调失败 | Device框架置ERROR；后续App_Stop不享受READY短路，但框架拒绝再次stop。后台“继续重试”不等于已具备恢复成功能力 |

单所有者使这些写入不会成为跨任务数据竞争，但不同入口仍可能对同一轮的进展、错误及完成时机作出不同决定。必须区分“资源事实后来改善”和“原事务最终回复是否成功”，不能为了合并状态而修改固定回复。

## 6. 问题与严重程度

### P1-R1：未来普通Stop双推进，需在C2.2B前收敛

- 位置：app_camera.c:491–507与301–329，资格调用点app_camera_qualification.c:363–382。
- 事实：两处都执行App_CameraStop、检查Bridge并写running/stopping/停止确认；没有同轮排他协议。
- 当前可达性：新回调未激活，不能作为当前固件已发生的新缺陷。
- 风险：直接业务接入后，BUSY/失败使轮末再次推进；错误/确认与生命周期回复的推进所有者不唯一。
- 最小方向：选择唯一普通停止推进口；资格层提出停止意图并消费资源结果，不另行执行硬件Stop。具体生产整改须另行授权。

### P2-R2：旧故障路径失败后可同轮重复BSP，原有行为

- 位置：camera_capture.c:529/560/610、757–765；app_camera.c:209、309。
- 事实：失败保持ERROR，后续入口可再次尝试；BSP控制锁只防重入，不防顺序再次进入。
- 影响：可能叠加停止等待和HAL重建开销；本轮没有实测耗时，不宣称造成视频/IPC异常或硬件损坏。
- 不应借本次文档审计擅自删除Media保护性停止或修改BSP。

### P2-R3：自动Device停止返回值被忽略，真实失败不能靠重试自动消除

- 位置：app_camera.c:129–131、116–119；device.c:264–280。
- 事实：App_CameraRun丢弃App_CameraStop结果；Device回调失败后置ERROR，后续框架Stop返回INVALID_STATE。
- 场景：Media已停止，自动Device stop先失败；随后Finish获得的可能是INVALID_STATE，不能把它理解成原传感器停止成功或原错误原因。
- 限制：原Media last_result/fault可能已保留更早采集错误；不能一概声称故障信息全部丢失。没有发现强制释放帧，但未形成完整Device ERROR恢复策略。

### P2-R4：现有专项没有覆盖组合调度和真实Device状态门控

- adapter_test.c:100–108验证Bridge BUSY后再次调用资格核心，没有在两次调用间运行真实App_CameraProcess→Bridge→Finish。
- qualification_test.c:216–218使用纯Stop回调桩，也没有组合旧轮末推进。
- 适配专项复用Tests/CameraModuleB1/behavior_test.c:131的Device_Stop桩。该桩不实施真实Device_Stop的RUNNING/BUSY/ERROR入口检查，不能据它证明ERROR后是否再次执行生命周期回调。
- 既有测试有价值，但历史162项PASS不构成本轮新增组合场景的验证。本轮不修改原测试，也不运行或宣称新增测试PASS。

未确认P0：没有证据证明当前新资格回调已经执行、帧被强制释放、同一成功路径连续两次写传感器停止寄存器，或发生IRQ内阻塞Stop。本轮不把这些写成结论。

## 7. 唯一停止推进所有者：建议契约（未实现）

### 7.1 所有权分层

- 唯一任务执行者：CameraTask；USB/Storage/Control不得直接调用上述资源Stop。
- 唯一Application资源权威：App_Camera；不把资格表或帧账本移给Task。
- 建议CameraTask调度内的唯一普通Stop推进点：App_CameraFinishRound，保留Media→Bridge→Finish的原顺序。其他业务/资格路径只记录停止意图及等待/读取结果，不能各自执行一遍App_CameraStop。
- Media内部故障保护仍允许立即尝试必要硬件停止；它不是另一个业务协调器。其本轮是否已尝试、成功/失败和DRAINING事实应被普通推进点消费，不能在没有明确策略时在同轮盲重试。
- BSP/Device只执行受控的一次实际操作，内部重入锁不能代替Application的每轮推进约束。

这是推荐的职责设计，不是现有代码已经做到，也不是本轮编码授权。独立Snapshot及显式App_CameraStop调用契约须保留；不能为了统一任务内推进而擅自删除单帧功能或改变其释放顺序。

### 7.2 后续整改应满足的约束

1. 一个round内，普通资源停止最多推进一次；保护性Stop已执行时，同轮消费其真实结果，下一轮才允许策略规定的重试。
2. 不能只在资格回调中加一把锁：该回调返回后锁已释放，后续Finish仍可进入。
3. 不能仅凭resource_stop_confirmed/READY代替完整停止验证；仍保持Stop、IsStopped、Device及Bridge各自的完成语义。
4. 资格回调即使改为意图/观察，也不得在普通推进点尚未确认时返回成功；Core保持原STOP请求未完成。结果已DECIDED后不再执行资源操作。
5. 业务普通Stop的等待不能阻断Bridge和Storage归还；没有超时强清引用或资格。
6. 保护性停止、资源状态与生命周期回复需由明确适配衔接，但不增加第二份running/stopping、第二套Replay或万能AppManager。
7. 不在本轮选择具体新增字段/API；后续实现需评估是否需要一个所属Task内部的round/attempt事实，而不是复制资源状态。

## 8. 测试设计（24项，全部未实现、未运行）

### 8.1 观测与测试分层

新增测试应运行真实App_Camera与真实CameraTask_Process顺序，记录round_id、调用来源、Media/Device前后状态、Bridge状态、返回值及各层计数：

- N_app_stop、N_media_stop：上层调用计数。
- N_bsp_stop、N_hal_dcmi_stop：实际底层入口计数。
- N_device_stop_api、N_device_stop_callback、N_sensor_stop_write：框架调用与实际硬件动作分别计数。
- running/stopping/resource_stop_confirmed、旧ACK/FAULT、原Rx completed/固定回复及session_closed。
- USB/SD各自引用、Return/ACK与OnStopped次数；仅使用真实Media账本或明确证据桩。
