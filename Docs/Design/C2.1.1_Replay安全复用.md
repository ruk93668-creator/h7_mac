# C2.1.1 Replay安全复用：实现契约

## 基线与范围

基线main@182c84e7334f0a62d96f1d3109b0d7fb8efb8158。
分支codex/stage-C2-1-1-replay-reuse。
仅新增普通C协议工具，不接入Camera/USB/Storage START/STOP，不建立资格表，不讨论或更改帧归还。不在正式固件实例化管理对象。

原C1/C1.1文件、56B消息、52B帧消息和三条四项生命周期队列均保持不变。旧ReplayRetire仍拒绝成功。

## 四个编号域

USB→Camera、Storage→Camera、Camera→USB、Camera→Storage分别拥有Tx和Rx对象。对象Init绑定source/target/consumer_id，运行期拒绝重复Init。回复回显原编号，不产生新请求编号。

request_id跨session/generation递增，允许跳号，禁止之后使用跳过的较小编号。ReserveIds只在EMPTY时调用，失败不改变分配上界和输出。issued_through只在Stage成功时推进，READY取消不回退。预留清理编号必须按实际发送顺序使用，不能在发出较大编号后再使用较小预留编号。

当前工具不定义Camera会话或消费者资格。格式合法但业务身份失效的请求，应由未来业务使用者给出稳定失败结果。工具本身不得据generation或completion_flags释放资源。

## 发送端

```text
EMPTY → Reserve/Stage → READY
READY → Flush失败 → READY（原文与编号不变）
READY → CancelReady → EMPTY（issued不回退）
READY → Flush成功 → WAIT_REPLY
WAIT_REPLY → 匹配回复 → COMPLETE
COMPLETE → GetCompleted → COMPLETE
COMPLETE → ConfirmConsumed完整原请求 → EMPTY
```

TxStage要求固定方向、REQUEST、合法消息、已预留编号及id>issued_through；同原请求重复Stage返回ALREADY_EXISTS，新的请求在旧Pending未消费前返回BUSY。未预留、倒退或取消后复用编号返回PROTOCOL。GetCompleted只复制回复，不释放下一请求入口。

ConfirmConsumed使用完整56B原请求比较，并再次核对其与终结回复的匹配关系；错误session、generation、来源、目标、操作、关联编号或正文不能消费结果。确认由所属模块在处理结果后显式调用，它不证明业务资源完成。

没有WAIT_REPLY超时清除接口。任务应继续处理反方向消息、回复及其他既有工作，不能同步阻塞等一个请求完成。反方向请求的回复使用Rx.reply_pending，与本方向Tx.pending独立。

## 接收端与候选槽

```text
无当前事务 → HELD候选 → Promote → 当前执行中
当前执行中 → Complete → 终结回复待提交
终结回复待提交 → FlushReply成功 → 完成且保留Replay
完成且保留Replay + 合法后继HELD + 无旧待发回复 → Promote接替
```

候选状态固定为EMPTY、HELD、QUARANTINED。后两者不能混用：

- 当前事务未终结，或者终结回复从未入队时到达更大请求：保留原候选并设为QUARANTINED、锁存protocol_fault，不执行新请求。
- 后来旧回复提交成功也不解除隔离；没有Reset或自动恢复API。
- 原当前事务仍允许Complete、FlushReply及相同请求重放，协议故障不执行资源清理。
- 原回复曾提交，但重复回复尚待发送时到达的正常后继可保留为HELD，Promote暂返回BUSY。
- 相同候选原文合并；不同候选不得覆盖原候选，并锁存隔离故障。

固定候选槽优于队列头保留：Camera收件箱同时承载两个消费者及反方向回复，不能让USB候选阻挡Storage或Camera发起事务的回复。现有Receive无需增加Peek接口。

## 请求判定顺序

1. Validate及固定方向检查，错误大编号不更新水位。
2. id等于当前：先完整比较原文，不把修改generation误当成另一事务。
3. 相同原文且未完成：DUPLICATE_RUNNING，不重复执行。
4. 相同原文且完成：REPLAY，原回复待发槽合并。
5. id<=退休高水位，或者id小于当前编号：STALE，拒绝执行。
6. 候选占用：仅合并相同原文；冲突或第二个不同后继为协议违例。
7. 首次请求或合法后继完整保存到HELD；非法提前后继保存到QUARANTINED。

内部分类不是业务回复。STALE/冲突返回PROTOCOL，不伪造终结BUSY。内部Promote背压返回BUSY，调用者保留HELD等待，不把它发送为终结业务结果。

退休后只保证旧编号拒绝，不保存所有历史正文；不能声称仍可逐字比较所有历史请求。同当前编号或候选编号的不同正文则可精确判定冲突。

## 安全接替提交顺序

Promote先检查候选、编号、旧完成状态、final_reply_enqueued和旧回复Pending为空；输出不得与管理对象重叠。

1. 在局部临时AppLifecycleReplay_t中调用原ReplayBegin构造新记录。
2. 构造失败：旧Replay、旧水位、候选和输出全部不变。
3. 进入单所有者提交区：先把退休高水位推进到旧active_request_id。
4. 安装临时Replay和新active_request_id。
5. 清零新事务final_reply_enqueued，消耗候选槽。
6. 输出完整新请求，结束api_busy保护，然后允许业务使用者执行一次。

提交区没有消息、业务或Observer回调。没有先清旧Replay再更新水位。Promote成功只交付一次；没有候选时返回NOT_FOUND。

api_busy是同对象回调重入保护，不是跨任务互斥锁，不改变IRQ/PRIMASK/RTOS语义。每个对象只能由绑定方向的所属任务串行操作，其他任务和ISR不得直接读写结构字段。

## 回复与安全边界

Complete复用原ReplayComplete固定终结回复，失败/BUSY不能被之后成功覆盖。RxFlushReply只提交与当前Replay完全匹配的回复。成功后锁存final_reply_enqueued并清理已提交的回复Pending，Replay仍保留。

原回复提交事实与当前是否有重放待发工作分开。完成、ACK入队或超时都不能单独退休；只有正常后继到达且上述检查通过才接替。

严格发送契约下，正常后继意味着发起者已消费前一匹配回复。接收端能够发现回复首次未入队时的提前后继，但无法从不变的56B消息中独立识别所有绕过受控Tx接口的发送行为。本方案不声称抵御恶意同核任务或任意直接写管理对象。

## session=0查询与身份变化

SESSION_QUERY使用同方向的编号。当前查询重传返回缓存原session；退休查询一律拒绝，不用旧request_id生成新查询结果。会话或代次变化不清除高水位。重新查询必须使用新编号。

编号耗尽拒绝新分配，不回绕。当前终结回复仍可重放。只覆盖配套固件完整启动后的单运行期，不实现单核热复位、任务私有状态丢失或持久化会话恢复。

## ABI、内存与栈

ARMCC5 O0/O2均验证：Tx=144B，Rx=332B，Pending=116B，Replay=120B；Tx.pending偏移28，Rx.replay偏移40、reply_pending偏移160、candidate偏移276。

未来四方向完整对象预算1904B（Camera952B、USB476B、Storage476B）。本轮无业务实例，正式Map确认新工具编译后因未调用被移除，正式静态RAM和现有任务栈增量均0。

未注入故障的独立调用图显示RxPromote局部栈O0为144B、O2为152B，已知调用链深度均200B。发送接口存在间接回调，静态已知深度不包含完整回调/中断链；未来接入仍须重新核对任务栈，不能把本次模拟值当作实板余量。

## 接口与禁止事项

Tx提供Init、ReserveIds、Stage、Flush、AcceptReply、GetCompleted、ConfirmConsumed、CancelReady。
Rx提供Init、ReceiveRequest、Promote、Complete、FlushReply、GetStatus。

全部返回SysResult_t；ReceiveRequest额外输出本地分类。初始化要求对象预先清零。管理对象字段不向业务开放直接修改；没有ClearReplay、Reset、高水位回退或强制退休API。

本阶段不接资格表、不接START/STOP、不修改Frame Lease、Media/FIFO/Bridge/Device，不新增任务、不使用动态内存，不实例化正式业务对象。
