# USB从约16 FPS恢复25 FPS：逐步定位高频栈余量扫描

记录日期：2026-11-08。工作分支：`codex/stage08b-sdmmc-idma`。修正与采样清理提交：`8c8195e`。

**状态：保持旧C组测试配置、未触发SD读写，将全部任务的栈余量扫描改为每1000ms最多一次，并移除临时USB耗时采样后，用户实板反馈USB恢复25 FPS。本分支尚未合并main。**

本篇只记录本次约16 FPS问题，不与早期三缓冲吞吐不足、USB枚举故障或M-V长期增长合并解释。恢复25 FPS不代表端到端延迟问题也已解决。

## 面试复述

我在接入SDMMC只读压力测试时，发现相机仍约30 FPS，但USB从25降到约16 FPS。最开始怀疑SD读写、缓冲区位置和任务调度，所以先把这些因素拆开做对照。

关键反例是：C组没有设置读写request，USB也会降帧；保留压力代码和缓冲、只不创建SdTest时又恢复25。后来增加可调轮询周期，20ms也正常，但退回旧C组又能稳定复现16。因此我没有把20ms轮询、SD带宽或内存位置直接当成原因。

接着对比USB抓包，发现两种固件协商的都是25 FPS、每帧38400字节，异常版本也能收齐完整帧，但帧内反复出现空槽，整帧周期约63ms。于是我从排查图像内容转向检查每包续发的时间。

第一轮采样发现HAL提交很快，但完成回调到任务确认存在长短两种路径。第二轮把通知、等待返回和任务入口拆开后，发现长路径不是任务一直没有被调度，而是完成中断发生时，UsbTask还在执行上一轮的尾部代码。第三轮继续包围Bridge、状态发布和栈扫描，测到栈扫描每次约552～579微秒；能匹配到的9次长延迟全部发生在扫描期间。

我随后将Camera、USB、Control、IPC和SdTest的栈余量扫描限制为每秒最多一次，其他C组配置和业务流程保持不变，删除临时测时插桩，重新烧录后用户确认恢复25 FPS。这个过程定位了高频诊断扫描对USB续包的直接影响，但旧C组与可调轮询固件为什么进入不同运行节奏，没有独立证明，不能讲成已经查明的相位机制。

## 起点：SD测试通过，但视频帧率下降

阶段08B完成4-bit、40MHz识卡与IDMA读写后，运行了5分钟只读压力测试。用户反馈测试结果符合预期，视频和OLED仍工作，但USB只有约16 FPS。随后确认OLED显示Camera约30 FPS。

当时并不知道栈扫描是原因。最初的问题包括：是否SD传输占总线、压力缓冲影响其他模块、CPU复制过多、UsbTask没有及时处理，或者只是电脑端统计误读。

5分钟压力测试本身记录了846轮全部完成，I/O、CRC及缓冲错误均为0，约300064ms后结束。它说明这轮只读压力没有报错，不证明USB性能没有受影响，也不是裸SD持续带宽测试。之后必须把“压力正在执行”和“只链接压力代码、request为0”分开。

### D组为什么不是简单把BLOCK设为0

实际D组提交`36ea40b`使用`APP_SD_BLOCK_D_GROUP_ENABLED`和一个运行期读取的`const volatile`门控变量，在创建任务前返回。BLOCK和STRESS仍开启，代码及缓冲保留，避免它们因整个模块关闭而被链接器删除。因此不能把D组写成“BLOCK=0、STRESS=1且所有内容自然仍链接”。

### 可调轮询版正常是重要反例

`6bc08f8`增加了可调轮询代码；用户在默认20ms、尚未修改Watch周期时，USB就为25 FPS。随后`7ec3878`恢复旧C组，再次得到16 FPS。

这不是“把周期改成1000ms已证明有效”。同为20ms的不同实现也有不同结果，因此不能只用轮询周期数值解释问题。代码、数据布局、启动和运行相位等都是候选差异；没有独立实验证明其中某一项就是触发路径。

## 第一阶段：看计数、配置与抓包，确认慢在哪里

### 先排查是否相机断供或桥接积压

- Camera约30 FPS，而USB约16，先集中在交付与USB发送部分。
- acquired、submitted、released持续增加，消息拒绝和队列重试未显示明显积压。允许一帧在途，不要求瞬时计数完全相等。
- 现场确认帧长度`0x9600=38400B`、最大Payload总长`0x03FF=1023B`。
- 帧间隔`0x61A80=400000`，按100ns单位为40ms，即协商25 FPS。

配置值只能说明申请或协商能力，不是实测FPS证明。Watch不是原子快照，不能由某两个瞬时计数相等排除所有竞争。

### 异常与正常USB抓包对照

当时用Wireshark/USBPcap抓USB传输，解析得到以下两个捕获窗口：

|项目|异常C组捕获|正常参考捕获|
|---|---:|---:|
|完整帧|208|165|
|每帧有效图像字节|38400|38400|
|每帧UVC包数|38|38|
|每帧包长|37包1023B，末包625B|37包1023B，末包625B|
|帧起点平均周期|约63.053ms|40ms|
|由帧起点计算的速率|约15.860 FPS|25 FPS|
|首包到EOF|约55ms|37ms|
|EOF到下一帧首包|约8ms|3ms|
|捕获中ISO错误计数|0|0|

两种捕获中完整帧的字节数一致，未记录到Payload错误位或FID未正常结束的完整帧。因此本次重点不是“所有图像被截断”，而是包之间等待变长。

异常捕获的帧内反复出现约1ms、2ms的有效包间隔；正常捕获可以连续发完38包，再留帧间间隔。零长度槽表示该主机ISO槽没有交付图像数据，不等于报告了CRC错误，也不能仅凭空槽断言设备没提交还是主机没取走，仍要看设备侧。

源抓包曾使用同名`1.pcapng`，之后被覆盖；两次分析汇总当时保存在`tmp/UsbPcapReview/capture1_analysis.json`和`capture2_analysis.json`。tmp不是仓库长期证据，本篇保留关键数值；不能把当前同名抓包默认为旧捕获。

## 第二阶段：第一轮设备采样，发现1ms/2ms节奏

提交`d238499`加入有限采样，不打印、不改变原传输确认及所有权规则。手动触发，最多512条，满后冻结；主循环在确认写者结束后处理Cache，使Keil能导出稳定记录。

观察点为DataIn、任务确认、下一包提交、HAL进入/返回及整帧完成。计时使用原有TIM6与HAL Tick组合的墙钟，并保留DWT周期及USB帧号。DWT在WFI期间可能停计，不能单独用它计算包含睡眠的等待。没有为采样重新配置时钟或清零共用DWT。

第一轮用户确认USB约16 FPS。512条记录全部有效，包含102次DataIn、102次确认及提交观察点，没有提交错误。

- HAL进入到返回约25μs；提交到HAL进入约6～7μs。
- 帧内确认到下一次提交通常约111μs。
- 短路径完成到任务确认约20μs，随后约1ms收到下一次完成。
- 长路径完成到任务确认约342μs，确认时USB硬件帧号已增加，随后完成间隔约2ms。
- 两个整帧完成点相隔62960μs，对应约15.88 FPS；这只是一个短窗口的帧间隔，不替代长期FPS测量。

当时只能说完成后的续包路径存在等待，不能直接说“FreeRTOS调度耗时342μs”或“HAL搬运占了1ms”。HAL根据提交时的硬件帧号配置ISO目标奇偶帧，与空槽现象相关，但采样没有记录HAL内部精确写寄存器和FIFO的瞬间，不能补造已证明错过某个主机Token的结论。

## 第三阶段：拆开通知、等待返回和任务入口

提交`754c9b9`增加通知前/后、等待前/后、任务处理入口、UVC入口及SOF观察点，仍不改变原调度策略。

### 先识别一次无效取流窗口

第一次细分导出虽然为READY、512条完整记录，但覆盖约2.56秒，只有每20ms一次的任务超时返回，USB帧号始终为577，没有SOF、DataIn或提交事件。

这轮不能用来解释16 FPS。它只能说明采样窗口内没有观察到正常USB帧活动，不能直接认定断线、播放器未启动或板卡故障。要求重新保持播放器取流、帧数增加，再触发采样；不能暂停后一直不恢复，就拿这段窗口分析发送延迟。

### 重新采到视频传输后，修正“调度延迟”的判断

重新导出包含29次可配对完成事件，墙钟记录均有效：

|阶段|实测表现|
|---|---|
|DataIn到通知开始|2～3μs|
|通知函数调用|5～7μs|
|通知返回到等待返回|14次约7～8μs；15次约335～578μs|
|等待返回到任务处理入口|2～3μs|
|任务处理入口到UVC入口|8～9μs|
|UVC入口到完成确认|3～4μs|

15次长路径中都经过一个SOF，14次短路径没有。关键例子按DataIn为零点：

```text
DataIn完成                    +0μs
通知返回                      +8μs
下一次SOF                   +302μs
UsbTask开始调用下一轮等待     +337μs
等待立即返回                 +343μs
任务处理入口                 +345μs
UVC入口                      +354μs
完成确认                     +357μs
```

等待调用在通知之后才发生，且很快返回。这说明DataIn到来时，UsbTask还没完成上一轮尾部，并不是一直阻塞着却几百微秒得不到调度。

中断通知不会重新创建或重新进入一份`UsbTask_Run()`。任务常驻`for (;;)`；中断返回后，原本执行到哪里就继续执行，通知挂起，等下一次等待返回和处理入口再消费。

|---|---:|---|
|UVC处理|36|3～153μs；无待发送工作与实际构包不是同一种路径|
|Bridge处理|36|8～9μs|
|Bridge返回到状态发布前|36|3～4μs|
|状态发布|36|4～5μs|
|栈余量扫描|36|552～579μs，平均562.5μs|
|栈扫描结束到下一轮等待前|36|1～2μs|

能够配对通知与确认的17次中：

这把长延迟缩小到了具体扫描区间；Bridge和状态发布的实测开销远小于它，不再把所有尾部代码笼统称为“任务调度慢”。

## 为什么栈余量查询会这么慢

当前源码调用链：

```text
UsbTask_Run循环尾部
    → uxTaskGetStackHighWaterMark(NULL)
    → prvTaskCheckFreeStackSpace()
```

FreeRTOS初始化任务栈时填入`0xA5`。`prvTaskCheckFreeStackSpace()`从栈边界逐字节读取仍保留填充值的区域，遇到被改写的字节后停止，再换算为Word数：

```c
while (*pucStackByte == (uint8_t)tskSTACK_FILL_BYTE)
{
    pucStackByte -= portSTACK_GROWTH;
    ulCount++;
}
```

本次一个扫描结果为1940 Word，即约7760字节，需要约7760轮读取、比较、地址移动、计数与跳转，不是读取一个已经维护好的剩余量变量。具体耗时还受编译结果、指令执行和中断影响；本轮没有逐项拆出这些成本，也没有证明某个优化等级就是原因。

这个返回值表示历史最小剩余栈空间，不是瞬时余量。原来每个SOF或完成通知引起的任务循环都可能扫描一次，诊断功能反而反复占用发送关键路径。

## 为什么是稳定16，而不是偶然掉一帧

已经观察到的是帧内约1ms/2ms交替、整帧约63ms的重复节奏。任务优先级、循环内部调用顺序、SOF周期和上一次提交决定的后续完成时刻都有规律，不能把RTOS理解成每轮随机排序。因此，稳定复现并不反驳时间预算问题。

但“为什么旧C组形成这一节奏，而可调轮询版没有”仍未完整归因。需要保留的边界：

- SdTest优先级1、UsbTask优先级4，不能直接说低优先级SdTest抢占了UsbTask。
- 20ms唤醒本身不是充分原因，可调版在20ms下曾正常。
- 正常版本没有做同等栈扫描测量，不能假设它也一定是0.56ms。
- 代码/数据布局、初始相位、执行指令差异可能影响表现，但没有独立证明哪个因素触发了差异。
- “碰巧避开”“Cache冲突”“总线拥堵”“SD IDMA抢带宽”均不能写成本次已证实的根因。

可以确定的是高频栈扫描造成了直接可见的续包延迟；不能把整个旧C组与可调版的差异机制说成已穷尽。

## 修正：低频统计，保留业务和所有权规则

用户先要求USB栈扫描每1000ms一次，随后扩大为全部栈扫描，并要求删除全部耗时测量代码。最终提交`8c8195e`：

1. Camera、Usb、Control和IPC任务分别保存自己的扫描时刻，每经过1000ms最多扫描一次。
2. SdTest普通结果路径与压力路径共用任务私有计时，避免两处叠加扫描。
3. 使用无符号Tick差值，处理回绕；长时间阻塞后只扫一次，不追补扫描。任务不运行时不会新增唤醒来做统计。
4. 不改变任务优先级、BOOT、业务等待周期、原SD的20ms轮询、压力代码与AXI缓冲、Camera/Media、USB协议和帧所有权。
5. 移除固件测时钩子、编译开关、记录器源文件注册及专用AXI记录区；保留PC解析器和历史结果。

此时C组仍为BLOCK=1、STRESS=1，写测试关闭，实板复测保持`g_sd_block_test.request=0`。没有用关闭整个SdTest来取得最终结果。

## 最终实板反馈与结论边界
